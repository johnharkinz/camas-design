# Camas — Visual Direction Exploration

## Objective

Explore several genuinely different visual directions for Camas before committing to a design system.

The aim is not to produce final polished screens.

The aim is to discover which visual language is worth developing further.

## Context

Camas is a home for small, practical web-development tools.

The initial launch includes:

- camas.dev — the main website
- Shareable — a web app
- Noggin — a browser extension
- Bonce — a browser extension

The existing logo, icon, colours, typography and layouts are not fixed.

Treat the current visual identity as disposable.

Read:

- `docs/project-brief.md`
- `AGENTS.md`
- relevant files in `docs/decisions/`

before starting.

## What to explore

Create **four genuinely different visual directions**.

Each direction should feel like a distinct design idea rather than a variation created by changing a font, accent colour or border radius.

The directions should differ meaningfully in areas such as:

- typography
- composition
- density
- visual rhythm
- use of colour
- shape language
- hierarchy
- brand expression
- interface treatment
- overall personality

Avoid converging immediately on a familiar developer-tool or SaaS aesthetic.

## Required outputs for each direction

Show enough of each direction to judge whether it can work across the full Camas family.

Each direction should include:

### 1. Camas identity

Show how the Camas name is treated.

This does not need to be a finished logo.

It can be:

- a wordmark
- a typographic treatment
- a simple identity idea
- a relationship between name and symbol

Do not force an icon or symbol if the direction does not need one.

### 2. camas.dev

Show a substantial homepage concept.

It should demonstrate:

- overall page composition
- navigation
- typography
- hierarchy
- product presentation
- brand personality

The homepage should feel like a home for useful web tools, not a generic startup landing page.

### 3. Shareable

Show a representative product screen.

Use a realistic state with:

- URL input
- overall result/status
- metadata or diagnostics
- successful and problematic information
- clear hierarchy

The UI should make technical information understandable without making it simplistic.

### 4. Browser-extension UI

Show one realistic compact browser-extension interface.

Use a constrained popup size rather than a large desktop canvas.

It should demonstrate:

- compact hierarchy
- controls
- states
- typography at small sizes
- how the visual language survives in a dense interface

This does not need to distinguish Noggin and Bonce yet. The purpose is to test the design system at extension scale.

### 5. Design language

For each direction, show or describe:

- typography approach
- colour approach
- spacing and density
- control style
- shape language
- icon or graphic approach if relevant

Do not treat these as disconnected style choices. Explain how they work together.

## Desired qualities

The strongest directions should feel:

- clear
- simple
- modern
- considered
- useful
- calm
- trustworthy
- precise
- pleasant to use

They should have personality without becoming decorative or distracting.

The tools should feel more restrained than the main marketing site.

## Avoid

Do not default to:

- generic SaaS landing pages
- default Tailwind/shadcn styling
- dark developer dashboards
- terminal aesthetics
- gratuitous gradients
- neon glows
- decorative blobs
- excessive glassmorphism
- oversized rounded cards everywhere
- generic geometric sans-serif plus blue accent
- branding that overwhelms the tools

Do not make all four directions variations of the same aesthetic.

## Range

At least one direction should be relatively restrained.

At least one should be more distinctive or expressive.

At least one should explore a design language that would not immediately be identified as a typical software/developer-tool product.

The fourth direction should be a strong alternative rather than a compromise between the others.

## Evaluation

For each direction, briefly explain:

- the core idea
- why it fits Camas
- what makes it distinctive
- where it works particularly well
- where it may struggle
- how well it scales from marketing site to compact product UI

## Important

Do not ask the project owner to choose fonts, colour values, spacing scales or similar design-system details before producing the concepts.

Make informed design choices and show the result.

The purpose of this exercise is to give the project owner strong things to react to, not to make them act as the designer.
